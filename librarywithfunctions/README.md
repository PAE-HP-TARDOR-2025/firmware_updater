# Firmware Update Library

This folder holds a self-contained snapshot of the core building blocks that power the CANopen firmware update flow without the rest of the demo scaffolding. Use these files as the starting point for integrating the OTA logic into other applications or for diffing against future changes in the demo projects.

The slave Object Dictionary copy already includes the firmware-transfer cluster (`0x1F50` download FIFO, `0x1F51` control, `0x1F57` metadata, `0x1F5A` status), so you can verify the entries before wiring them into your own project.

## Layout

- `master/OD.[ch]`
	- Direct copy of the controller Object Dictionary (`demo/demomaster/canopennode`).
	- Keep this file in sync with whatever CANopen stack you run on the actual master so the SDO indices stay aligned.
- `master/fw_master_update.[ch]`
	- Reusable helpers for loading binaries, computing CRC-16, and exercising the CiA 302 firmware objects (`0x1F50–0x1F5A`).
	- All CAN transport calls are stubbed with logging; swap them with your `CO_SDOclient*` interactions.
- `slave/OD.[ch]`
	- Copy of the OTA-capable slave Object Dictionary (`demo/demoslave/canopennode`) with the verified firmware objects in place.
- `slave/fw_slave_update.[ch]`
	- Platform-neutral state machine that validates metadata, checks chunk ordering, tracks CRC, and reports readiness to boot.
	- Keep this around for host-side tests, alternative RTOS ports, or as a reference model to compare against your production handler.
- `slave/fw_update_server.[ch]`
	- ESP-IDF ready SDO hook implementation that binds the firmware objects to OTA partitions (`esp_ota_*`, `esp_partition_*`).
	- Copy these into your component if you want the exact handlers that demoslave registers via `fw_server_init`.
- `slave/build_slave_bins.py`
	- Script originally used to produce the canned `hello.bin`/`bye.bin` payloads by compiling `demo/dummy_slave_main.c` with different greeting strings.
	- Run it from the repo root whenever you need to regenerate the demo binaries; it mirrors the workflow that produced the artifacts shipped in `demo/bins/`.
- `demo/master/demo_master_main.c`
## Demo Binaries & Firmware Sources

- The ESP32 slave that actually runs on hardware is `demo/demoslave/main/hello_world_main.c`, which registers `fw_server_init()` so CANopen object extensions point at the OTA handler.
- The canned payloads (`librarywithfunctions/demo/bins/hello.bin` and `bye.bin`) were generated by `slave/build_slave_bins.py`, which in turn compiles `demo/dummy_slave_main.c` with alternate greeting strings. The script is copied here so you can regenerate those bins without digging through the demo tree.
- When testing the upload flow, flash `hello_world_main.c` (or your real application) to the slave and then push the staged `hello.bin`/`bye.bin` images via the master demo to watch the greeting swap after reboot.
- `fw_slave_update.[ch]` remain a lightweight, platform-agnostic state machine you can embed in host tests or non-ESP targets; `fw_update_server.[ch]` simply wraps the same progression with ESP-IDF OTA primitives and CANopen extensions. Use whichever layer fits your integration point.
	- Boots the CANopen stack, builds an `fw_upload_plan_t`, and runs the helper-driven upload sequence end to end.
	- Use it as a template for wiring the master helpers into a production task (replace the stubbed SDO calls inside `fw_master_update.c`).
- `demo/slave/demo_slave_main.c`
	- Standalone firmware entry point that spins up CANopen and drives `fw_slave_update` through a scripted metadata/chunk/finalize session.
	- Mirrors the structure you would use when routing SDO server callbacks for `0x1F50/0x1F51/0x1F57/0x1F5A` to the helper functions.
- `demo/slave/hello_world_main.c`
	- Copy of the real ESP-IDF application flashed on the slave hardware; it registers `fw_server_init()` so the OTA objects hit the ESP-IDF-specific handlers.
	- Use this when you need to see the production wiring or rebuild the canonical binary that `build_slave_bins.py` eventually consumes.
- `partitions/`
	- `master_storage_spiffs.csv` – Custom partition map used by the ESP-IDF master so the `/storage` SPIFFS image has predictable space for firmware artifacts.
	- `slave_two_ota.csv` – Dummy two-OTA layout mirroring the ESP-IDF template that the slave consumes.

## How to Use the Master Helpers

1. Drop `master/fw_master_update.[ch]` into your host project and include `fw_master_update.h` from the task that drives firmware uploads.
2. Provide a `fw_upload_plan_t` describing the target node ID, bank, and chunk size. Example:

	 ```c
	 fw_upload_plan_t plan = {
			 .firmwarePath = "artifacts/bye.bin",
			 .type = FW_IMAGE_MAIN,
			 .targetBank = 1,
			 .targetNodeId = 10,
			 .maxChunkBytes = 256,
			 .expectedCrc = 0
	 };
	 fw_master_run_upload_session(&plan);
	 ```

3. Replace the stubbed helpers (`fw_master_send_metadata`, `fw_master_send_chunk`, etc.) with real SDO client calls:
	 - Metadata → download into `0x1F57` subindices.
	 - Control tokens (erase/start/finalize) → write to `0x1F51`.
	 - Firmware data → block download into `0x1F50`.
	 - Status polling → read back `0x1F5A` if you need progress.
4. The helper keeps CRC bookkeeping in sync with the slave implementation, so if both ends use the provided functions the computed value will match.

## How to Use the Slave Helpers

1. Add `slave/fw_slave_update.[ch]` to your ESP-IDF component and include `fw_slave_update.h` from the module that implements the CANopen SDO server callbacks.
2. Initialize a `fw_update_context_t` per node (or per OTA slot) and call:
	 - `fw_slave_store_metadata` when the master writes `0x1F57`.
	 - `fw_slave_prepare_storage` when `0x1F51` issues the erase/start token.
	 - `fw_slave_receive_chunk` from the handler that accepts SDO block segments for `0x1F50`.
	 - `fw_slave_finalize` when the master announces completion.
3. Once `fw_slave_finalize` succeeds, switch boot partitions, persist status into `0x1F5A`, and reboot (the demoslave auto-restart routine demonstrates the pattern).
4. `fw_slave_dump_context` makes it easier to log progress over UART during bring-up.

### Wiring Into `main_firmware_update.c`

The existing demo main already uses these helper functions, but if you are creating a new firmware:

```c
static fw_update_context_t fwCtx;

void app_main(void) {
		fw_slave_reset_context(&fwCtx);
		// inside your SDO 0x1F57 write callback
		fw_slave_store_metadata(&fwCtx, sizeBytes, crc, bank);
		// before enabling chunk writes
		fw_slave_prepare_storage(&fwCtx);
		// inside the 0x1F50 data handler
		fw_slave_receive_chunk(&fwCtx, dataPtr, dataLen, offset);
		// at the finalize token
		if (fw_slave_finalize(&fwCtx)) {
				esp_ota_set_boot_partition(...);
				esp_restart();
		}
}
```

## Partition References

- **Master (`partitions/master_storage_spiffs.csv`)**
	- Ensures `/storage` has ~320 KB for staged binaries while keeping a single factory app slot. Flash it with `idf.py -p <PORT> partition-table app storage storage-flash` when you rebuild the SPIFFS image.
- **Slave (`partitions/slave_two_ota.csv`)**
	- Mirrors ESP-IDF's two-OTA template with a dedicated SPIFFS region at the end. Point `CONFIG_PARTITION_TABLE_CUSTOM_FILENAME` at this file if you need deterministic offsets for testing.

You can drop these CSVs into any ESP-IDF project and set `CONFIG_PARTITION_TABLE_CUSTOM=y` plus the filename in `sdkconfig`. They serve as known-good templates when replicating the demo memory layout.

## Keeping the Library in Sync

- When the demo Object Dictionaries change, copy the updated `OD.[ch]` into this folder and re-run any auto-generation steps (e.g., CANopenNode's `od_editor`).
- Treat the helper `.c/.h` files as canonical references: diff them against the original demo files to understand upstream edits.
- Because the master/slave helpers intentionally log every step, you can plug them into headless CI tests and assert on UART output before integrating with real CAN hardware.

With these pieces you can spin up the full OTA pipeline in any CANopen-compatible product without dragging the entire demo tree into your repository.
